<a id="naming-override-response-revision-1"></a>
# Naming Override Response Revision 1

This is an independent response to the human ruling recorded in
[`proposal4.glm53m.md`](/constitution/naming/exploration/proposal4.glm53m.md),
and to the resumed responses in its companion and the three synthesis files.
My position is **extend**. The ruling is correct for Rekon's knowledge plane;
the surviving structures are sufficient for ordinary local work, but they need
one explicit composition law for sections and one portable-origin law for
artifacts that leave their tree.

This file does not mint a self-named actor. The six existing self-naming
precedents, including `steward/glm-5.3-max`, establish permission rather than
an obligation to create another actor. A bounded response has enough
attribution in `generated.by`, and adding an actor here would create a new
continuity promise without a demonstrated future consumer.

<a id="position"></a>
## Position

The tree is the knowledge namespace, so a path move is a disclosed knowledge
rename and not a neutral locator update. The missing precision is that an OKF
Concept ID names a document, while Rekon's section identity composes that
document ID with a pinned anchor and must not pretend to be another OKF
document. A standalone copy can preserve continuity only by carrying its
origin and relation; it receives a new canonical destination identity rather
than smuggling a move-stable stem back into the system.

<a id="what-the-ruling-settles"></a>
## What The Ruling Settles

The ruling and the resumed addenda settle four holdings. I adopt them without
trying to average them back toward the prior synthesis:

| Holding | Consequence in this response |
|---|---|
| Location-implied naming is identity | For tree-resident knowledge, the bundle path without `.md` is the document name. A pinned anchor composes the section name. |
| Rename ripple is accepted cost | A move is a human-gated identity migration. The bill is counted, not denied, and is paid with `naming-rename-covenant`, inventories, repairs, and compatibility. |
| Hats are declared actor aliases | A hat maps to one actor. `naming-role-is-relation` remains useful as a responsibility record, but it is not an exclusive replacement for the alias. |
| Cross-modal aliases are precedent | `rekon-con-naming` is a living work ID and evidence that a glossary component can cross media. `naming-alias-collapse` still guards ambiguous mappings. |

The narrower reading of one name also survives: one live canonical owner per
authority, with mapped resolution forms around it. A path can occupy both the
canonical-name and locator registers because register membership follows the
promise a value performs, not its punctuation.

<a id="location-changes-the-surviving-structures"></a>
## Location Changes The Surviving Structures

Location identity is not a replacement for the surviving compact. It changes
the source of one register entry and changes the classification of movement:

| Existing structure | Revised reading |
|---|---|
| `naming-name-promise` | The promise is continuity and disclosed change, not an eternal byte string. A path move keeps referent continuity only through an explicit rename record. |
| `naming-reference-registers` | The canonical-name row is the bundle path for a document and path plus anchor for a section. The locator row overlaps it for knowledge paths. |
| `naming-one-name-locality` | One current regular path owns one knowledge artifact per authority. An old path is a retired mapping or a historical observation, never a silent peer owner. |
| `naming-implied-names` | The path supplies the document prefix and the pinned anchor supplies the terminal segment. This is identity, not merely read-time expansion. |
| `naming-slug-at-mint` | The anchor segment is derived from the heading at creation and pinned. Moving the parent document changes the composed full name even when the terminal anchor is unchanged. |
| `naming-identity-change` | A file, directory, or docroot move is a canonical rename of its descendants. A display edit with a retained anchor is not. |
| `naming-native-authority` | Files own knowledge location and prose; Beads owns work IDs; actors own self-declared actor names; version control owns exact history. No plane is made universal. |
| `naming-home-not-layout` | Contract adoption and movement remain separate decisions. If movement happens, it is identity work. Promotion still normally synthesizes a maintained README rather than relocating evidence. |
| `naming-successor` | A new maintained home may be a successor even when it discusses the same subject. A path move alone is a rename; a synthesized maintained account is a supersession decision. |
| `naming-cross-modal` | A path, anchor, beads ID, YAML key, or diagram node can be a projection or alias when its mapping is declared. Equal spelling does not make cross-plane entities one entity. |

The last two rows matter together. The ruling does not turn every directory
cleanup into a semantic merger, and it does not turn every promotion into a
move. The canonical constitution already says that promotion is synthesis,
not movement at
[`doc-constitution-lifecycle-promotion`](/constitution/README.md#doc-constitution-lifecycle-promotion).
Location identity makes that distinction sharper: the synthesized README has
its own path identity and should explicitly supersede or derive from the
evidence it absorbs.

<a id="naming-section-composition"></a>
## naming-section-composition

This is the first new law I add. It resolves the boundary that the ruling
requires but does not name as a standalone rule:

```text
document_id(P) = bundle-relative path P without .md
section_id(P, A) = document_id(P)#pinned-anchor A
```

`document_id(P)` is the OKF Concept ID at document grain. `section_id(P, A)`
is a Rekon fragment identity at section grain. It is not a second OKF Concept,
does not acquire independent frontmatter, and does not create a second native
authority. The section inherits the containing document's status, generation,
verification, and stewardship unless a future producer extension says
otherwise.

The composition law has four parts:

1. `P` is scoped by an authority and a declared bundle boundary. A bare `A`
   is a contextual resolution form, not a globally unique section name.
2. `A` is explicit and pinned at mint under `naming-slug-at-mint`. A later
   heading edit can leave `A` stable, but a path move changes the full
   `section_id`.
3. Two files may use the same terminal anchor without collision because their
   full section identities include different paths. A duplicate anchor inside
   one file is still an ownership defect.
4. Extracting a section into a new regular file creates a new document ID and
   therefore a new section composition. Continuity is expressed by a sourced
   relation such as `derived from`, `moved from`, or `supersedes`; identical
   prose or an identical terminal anchor is not enough.

This is an extension of OKF, not a correction to OKF. OKF v0.2 section 2
defines Concept ID as the path of the concept file with `.md` removed, and
section 3 defines the bundle as a directory tree. OKF does not specify
fragments, actor names, Beads work IDs, or cross-project equivalence. Rekon
may compose a fragment identity while continuing to call only the document an
OKF Concept.

<a id="the-okf-boundary"></a>
## The OKF Boundary

The phrase "location is identity" has to be scoped twice: by authority and by
entity grain. Without those scopes, the rule overclaims.

At document grain, OKF supplies the receipt directly:

```text
bundle authority + path/to/concept
```

At section grain, Rekon extends that receipt:

```text
bundle authority + path/to/concept#pinned-anchor
```

The frontmatter `resource` field is not a hidden replacement for either form.
In OKF it identifies the underlying asset when one exists. It may point to a
URL, path, or scope descriptor, while the Concept ID remains the document's
bundle path. A source entry can cite an exact artifact without becoming the
current document's owner.

This boundary preserves the useful distinction between a document and its
sections without reviving the prior hidden-stem architecture. It also makes
the scope of `naming-reference-registers` testable: the path-plus-anchor value
can be canonical in the knowledge plane, while a session URL or routing string
remains only a locator in the actor or orchestration plane.

<a id="naming-portable-identity-envelope"></a>
## naming-portable-identity-envelope

This is the second new law. A tree identity is portable only with its origin
context. A standalone artifact, section extraction, or cross-project export
MUST preserve enough of the following conceptual tuple for an observer to tell
what moved, what was copied, and what was newly minted:

```text
origin authority
origin bundle boundary
origin document ID
origin pinned anchor, when the claim is section-grain
origin revision or evidence binding
destination authority and destination document ID, when known
continuity relation and disposition
```

This is a semantic requirement, not a prescribed YAML schema or resolver API.
The exact representation belongs at `naming-tool-seam`. The point is to stop
the portable document from making one of two false claims:

- that a path is globally meaningful without its old authority and bundle; or
- that copied bytes at a destination retain the old canonical name merely
  because their content looks the same.

The envelope does not make the origin path a second current owner. It makes the
old identity and the destination identity auditable members of a rename,
derivation, or supersession relation. If the old authority cannot be reached,
the envelope remains evidence of origin but cannot manufacture a live old-path
resolver.

<a id="standalone-travel-across-trees"></a>
## Standalone Travel Across Trees

The codex mandate in `proposal3b` is valuable precisely because a standalone
document can leave its library. Location identity changes what travel means.

| Travel operation | Destination identity | Required continuity claim |
|---|---|---|
| Read a file in place | The current origin path and any section composition | No migration claim; ordinary resolution follows the local authority. |
| Git-move a file inside one project | The new path and its composed section paths | `naming-rename-covenant` records predecessor, successor, authority, and compatibility disposition. |
| Copy a document to another tree | The destination authority plus destination path | A copy is a new artifact by default. Add `derived from` or `supersedes` if continuity is intended. |
| Extract one section into a standalone document | The destination document path, then its new anchor | The source section is an origin relation, not a surviving canonical name at the destination. |
| Expose a symlink or redirect | The target's identity | The exposure is a mapped resolution form, subject to host behavior; it is not a second regular body. |
| Quote a section or use a citation token | The source identity named by the citation context | The quote or token is a reference, not a new owner. |

The practical consequence is that "standalone" and "portable identity" are
not synonyms. A document can be understandable on its own while its canonical
name remains authority-relative. A portable artifact should carry its origin
tuple, but a receiving tree should not be forced to accept the origin as its
own path identity.

This is also where the promise/currency split applies beyond actors. The
origin steward may promise that the destination derives from or supersedes a
source. The receiving authority decides whether that relation has currency in
its own resolution surface. The destination's placement is its local identity;
the relation is what explains continuity across the trees.

## The Ripple In This Corpus

I measured the tracked corpus before this response file was added, on
2026-09-03. The commands were intentionally plain and reproducible:

```text

  --glob '*.md' --glob '!constitution/naming/exploration/draft1.*.md' | wc -l

  --glob '*.md' --glob '!constitution/naming/exploration/draft1.*.md' | wc -l

  --glob '*.md' --glob '!constitution/naming/exploration/draft1.*.md' | wc -l

rg -o 'constitution/naming' --hidden \
  --glob '!constitution/naming/**' --glob '!.git/**' | wc -l

```

The 16 files are the topic README plus 15 exploration files. Fifteen files
carry explicit anchors. They contain 415 headings and 398 explicit anchors;
the anchors use 313 distinct terminal strings. The repeated terminal strings
are not automatically collisions under the ruling because the containing
path disambiguates them. They would be harder to distinguish if a bare anchor
were exported without its origin envelope.

The 134 direct Markdown links and 86 frontmatter `resource` lines are inside
the naming subtree. They are not all identical obligations: a relative link
within the moved subtree can remain textually unchanged, while a root-relative
path or a source citation may need rewriting or deliberate retention on a
compatibility surface. They are the inventory to review, not a promise that a
blind substitution is correct.

Only two path occurrences are outside the subtree in the current tracked
corpus, both in `.beads/issues.jsonl`. One is the naming ticket's forward
anchor; the other is a work-graph reference to the audit. This makes the local
cost smaller than the abstract phrase "global namespace" suggests. It does
not bound future external citations, copied prose, other checkouts, or human
memory, so it does not remove the need for an old-authority compatibility
decision.

<a id="the-ripple-bill"></a>
## The Ripple Bill

For a proposed move of `constitution/naming/` to a root topic such as
`/naming/`, the minimum bill in this snapshot is:

| Surface | Count or condition | What must happen |
|---|---:|---|
| Regular document identities | 16 | Record 16 old-to-new path mappings. Every moved file receives a new Concept ID under OKF's rule. |
| Composed section identities | 398 | Treat each path-plus-anchor as renamed, even though the terminal anchor can remain byte-identical. Preserve deep-fragment mappings where consumers warrant them. |
| Direct root-relative naming links | 134 | Inventory each link. Rewrite controlled current references or leave an intentional old-path compatibility route. |
| Frontmatter resource paths | 86 | Review each path as current resource, historical source, or compatibility evidence. Do not rewrite historical evidence reflexively. |
| Outside work-graph path occurrences | 2 | Update the forward anchor and the audit reference deliberately, or record their old-path disposition. |
| Unknown external consumers | uncounted | Ask the old authority to preserve a route or accept visible breakage. No new authority can repair a namespace it does not control. |

The counts are additive only as a review checklist, not as a number of unique
files. The direct links and resource lines are syntax classes; some may point
to the same target. The identity counts are different: 16 document names and
398 composed section names change even if no body line changes.

The cost is not necessarily 398 manual edits. A directory symlink or a
fragment-aware compatibility layer could preserve many old routes. That
surface must be tested, because a file that opens does not prove that
`old-path.md#old-anchor` reaches the intended section. A regular compatibility
stub also needs care: under OKF, a non-reserved `.md` file with frontmatter is
itself a Concept at its old path. It is therefore a deprecated redirecting
artifact, not an invisible alias. A symlink can act as a resolution exposure
if the publication host follows it; a stub needs explicit status and target
mapping.

<a id="what-everyone-missed"></a>
## What Everyone Missed

The resumed responses correctly price unknown external citations, but they
understate four findings visible in this corpus.

<a id="the-local-corpus-is-mostly-self-referential"></a>
### The Local Corpus Is Mostly Self Referential

The feared global repair surface is not present in the current Markdown
corpus. The naming tree cites itself heavily, while the only outside path
occurrences are in Beads. The first migration should therefore be evaluated
as a local 16-file operation with a small work-plane tail, not as an imagined
planetary transaction. Unknown external use remains a risk category, not a
measured current dependency.

<a id="duplicate-terminal-anchors-are-evidence-for-path-identity"></a>
### Duplicate Terminal Anchors Are Evidence For Path Identity

There are 398 explicit anchors but only 313 distinct terminal strings across
the current naming tree. Generic anchors such as `cross-references` and
`mechanical-anchor-verification` recur across independent artifacts. A hidden
move-stable semantic stem would need a separate collision or qualification
story for these sections. The path-plus-anchor composition gets uniqueness
from the tree while preserving short local anchors for ordinary reading.

<a id="a-compatibility-stub-is-not-nothing"></a>
### A Compatibility Stub Is Not Nothing

The migration vocabulary says "stub" as though it were merely a pointer. OKF
says every non-reserved Markdown file is a Concept document. The two statements
can coexist only if the stub is explicitly a retired Concept with a mapping to
its successor, or if the publication surface supports a symlink/exposure that
does not create a second regular body. This is a representation obligation for
`naming-tool-seam`, not a reason to reject the ruling.

<a id="promotion-and-travel-have-different-identity-effects"></a>
### Promotion And Travel Have Different Identity Effects

The existing topic presence still carries `local_knowledge_id: agent-naming`
while its title and description say Naming. Under location identity that field
is a compatibility or indexing projection, not an owner above the path. More
importantly, promoting a synthesis into a maintained README should normally
create a new public document identity and supersede the evidence, rather than
physically relocating the evidence and calling that promotion. The corpus's
own model-suffixed wave files make this visible: their exact paths are useful
evidence identities, while a model-free maintained presence would be a new
current account.

<a id="cross-project-citation"></a>
## Cross Project Citation

Cross-project qualification is now more important, not less. A local identity
`P#A` is incomplete outside its bundle. A qualified reference needs at least:

```text
foreign authority + foreign bundle boundary + P#A
```

The authority is not just a project prefix. It should resolve to a canonical
repository or bundle surface that can state whether the path is current,
retired, private, or ambiguous. Matching `P#A` strings in two projects do not
prove sameness. A relation such as `equivalent to`, `derived from`, or
`supersedes`, with evidence, does that work.

Cross-project movement creates an asymmetric cost:

1. The old authority retires its old path and section identities, or keeps
   them as compatibility mappings.
2. The destination authority creates identities from its own tree placement.
3. Controlled references are repaired by their owners.
4. The old authority alone can preserve ordinary resolution of the old
   qualified names.
5. If the old authority is gone, the origin envelope can explain history but
   cannot restore a live route.

For immutable evidence, a commit-pinned repository URL plus exact path and
anchor is the stronger citation. For current wiki navigation, a qualified
logical path plus a resolution story is useful. These are complementary
register entries, not competing semantic names. The distinction is already
anticipated by the canonical constitution's link and evidence rules at
[`doc-constitution-references-links`](/constitution/README.md#doc-constitution-references-links)
and
[`doc-constitution-references-evidence`](/constitution/README.md#doc-constitution-references-evidence).

<a id="hats-and-cross-modal-aliases"></a>
## Hats And Cross Modal Aliases

The ruling's restoration is coherent with the narrowed one-name law. A hat is
a concern-scoped alias that maps to one actor. A role relation records what the
actor undertook, for which capability and scope, and under what history. One
action may need both:

| Value | Question answered | Canonical owner |
|---|---|---|
| Actor name | Who makes the continuity promise? | One actor |
| Hat | Which concern-specific string reaches that actor? | The same actor, by declaration |
| Role relation | What responsibility was undertaken? | A typed relation, not an actor |
| Model identity | What generated the artifact? | `generated.by`, not a hat |
| Session handle | Where can the execution be inspected? | An exact locator |

The same logic applies to `rekon-con-naming`. The full beads string names a
work entity in the Beads plane. Its `con` component is a cross-modal alias
component with recoverable meaning in this project. It does not collapse the
work ticket into this document, and it does not require every project to adopt
the same abbreviation. `naming-work-knowledge-seam` and native authority keep
the speech acts distinct.

No advance central permission is needed for a useful alias. A mapping becomes
an earned governance obligation when ambiguity, collision, export, or
maintenance volume exceeds what the nearby declaration can carry. The alias
must still be inspectable once it is used in a durable citation. "Ungoverned"
means no advance gate; it must not mean unmapped or unaccountable.

<a id="the-promise-and-currency-split"></a>
## The Promise And Currency Split

`naming-promise-currency-split` remains the right actor boundary and can be
extended cautiously to portable knowledge relations.

- The promise is unilateral where the named actor is concerned. An actor may
  self-declare its name and hats; another actor cannot forge that claim.
- Currency is bilateral. A receiving authority decides whether it resolves
  the actor and aliases in its scope.
- For a moved document, the steward may state a predecessor-successor
  relation, but the destination authority decides whether that relation enters
  its current resolution surface.
- Evidence of continuity is not the same as current ownership. A source,
  commit, or origin tuple can support a claim without becoming the destination
  path's owner.

This keeps the actor law from being over-generalized into a universal registry.
The tree is authoritative for where knowledge is currently named; the actor is
authoritative for its own identity promise; Beads is authoritative for work
lifecycle; version control is authoritative for exact historical state.

<a id="what-needs-new-law"></a>
## What Needs New Law

I recommend accepting the human ruling and adding only these two semantic laws
to the future naming compact:

| New identifier | Narrow law | Why existing structures are insufficient |
|---|---|---|
| `naming-section-composition` | A Rekon section identity is `document Concept ID + pinned anchor`; it is not an additional OKF Concept. | OKF settles document identity but leaves section identity open, while the ruling makes sections part of the full name. |
| `naming-portable-identity-envelope` | A standalone or cross-tree artifact carries authority, bundle, origin path, anchor, revision, destination, and continuity relation conceptually. | Federation and resolution describe relationships, but neither says what minimum origin context must travel with an extracted artifact. |

I do not add a separate law for compatibility stubs. The needed rule is a
corollary of `naming-identity-change`, `naming-rename-covenant`, OKF's
document rule, and `naming-convergence-repair`: a regular old-path stub is a
deprecated redirecting document; a symlink is a mapped exposure only where the
host honors it. The tool seam should later define how to encode and verify
those forms.

The canonical constitution needs a scoped amendment before the compact is
promoted. Its durable-identity principle currently says identity outranks
layout, and its anchor rule says anchors survive reasonable reorganization.
Those statements should become:

> A document's identity follows its declared bundle path. A pinned section
> anchor survives heading edits and numbering changes, but a file or directory
> move is a disclosed rename of the document and every section it composes.

This amendment does not require rewriting historical files. It changes the
prospective law and leaves their old claims as evidence, as the constitution's
evolution rules require. The hierarchy1 sentence that disposition replaces
location can remain, but it must be read as a trust and posture rule, not an
identity rule.

<a id="what-stays-in-the-nebula"></a>
## What Stays In The Nebula

The following questions remain open deliberately. The ruling settles the
direction, not every representation or governance detail.

- **Bundle root declaration.** Is a Git repository always the bundle, or can a
  subdirectory be an OKF bundle inside it? How is the boundary declared and
  discovered without making every path a global URI?
- **Authority identity.** What stable repository or project value qualifies a
  path across projects, especially when a project is renamed or mirrored?
- **Section metadata.** Should a high-pressure section ever carry its own
  steward, verification, or lifecycle distinct from the containing document,
  or is document inheritance always enough?
- **Extraction semantics.** When a section is copied, is the destination
  `derived from`, `supersedes`, or merely `quotes` the source? Content sameness
  cannot decide the relation.
- **Redirect representation.** Which hosts preserve deep fragments through a
  symlink, a regular deprecated stub, or a generated old-anchor map?
- **External citation burden.** How much compatibility does an authority owe
  unknown external consumers, and when is loud failure the honest choice?
- **Topology disclosure.** Does a fully qualified path reveal too much about a
  private project tree? Knowledge paths, actor names, and private resources may
  need different native conventions.
- **Alias discoverability.** When does an alias need a nearby declaration,
  topic glossary, checked register, or stronger governance? The pressure test
  should decide, not a universal entrance fee.
- **Renderer conformance.** Pandoc derivation is verified here; GitHub and
  other renderers may differ on punctuation, Unicode, duplicate headings, and
  explicit targets.
- **Old local projections.** When should `local_knowledge_id: agent-naming`
  be retained as compatibility, renamed, or retired after the topic's
  broadened referent is accepted?
- **Successor versus rename.** A maintained README, an evidence file, and a
  moved file may all discuss one subject while having different identities and
  different lifecycle promises.

These are not reasons to reverse location identity. They are the nebula around
the settled spine, where a premature schema or global registry would spend
ceremony before the corpus supplies pressure.

<a id="acceptance-and-migration-sequence"></a>
## Acceptance And Migration Sequence

The safest sequence keeps contract acceptance separate from layout movement:

1. Accept or revise the compact, including the two new laws and the scoped
   amendment to the canonical constitution.
2. Declare the bundle and project authority for the knowledge plane before
   attempting cross-tree references.
3. Build a resolver projection from current paths, pinned anchors, aliases,
   and native work records. Keep it derived; do not make it a second authority.
4. Run a move pilot on a small topic. Measure old-path resolution, deep
   fragments, frontmatter resource handling, and Beads forward anchors.
5. Use hierarchy1's migration map, inbound-link inventory, human gate, and
   compatibility choice for any actual move.
6. Promote accepted prose through synthesis. Leave model-suffixed evidence in
   place unless a deliberate identity migration says otherwise.
7. Treat a copied or extracted artifact as a destination identity with an
   origin envelope and explicit relation.
8. Run a doc-pass after the migration and record what remains unresolved. Do
   not silently fuzzy-bind retired names to plausible replacements.

This sequence demonstrates the ruling without using a production move as the
first test. It also preserves `naming-tool-seam`: the semantic invariants are
