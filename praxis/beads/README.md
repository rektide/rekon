# Beads work tracking

Use the project's existing tracker and work items. Ticketing is user-shaped:
ask when the desired level is unclear; do not create tickets to satisfy a
workflow. **Once using beads, readable IDs and explicit dependency semantics
are required.** Run `bd` from the project directory, rather than using `bd -C`.

## Ticket identity

Check `bd config get issue_prefix`. Always supply a stable, human-readable
`--id`; never accept autogenerated IDs. Name children under the epic:

```sh
bd create --id <prefix>-<effort> --title "<architectural outcome>" --type epic --priority P1 --description "<why and how the system fits>" --acceptance "<observable completion>"
bd create --id <prefix>-<effort>-<capability> --title "<concrete outcome>" --type feature --priority P2 --description "<implementation scope>" --acceptance "<verification>"
bd dep add <prefix>-<effort>-<capability> <prefix>-<effort> --type parent-child
```

An epic explains the purpose and architecture; children describe concrete work
and acceptance criteria. ID namespacing and a parent-child edge are both useful;
one does not create the other. Prefer updating or renaming existing work to
creating a replacement duplicate. `bd rename <old-id> <new-id>` rewrites native
references; review document links outside the tracker separately.

## Search, inspect, advance, close

```sh
bd list --status open --desc-contains "<topic>" --sort priority --limit 20
bd show <issue-id>
bd update <issue-id> --claim --append-notes "<findings, decision, next step>"
bd list --status open --ready --label <label> --limit 20
bd close <issue-id> --reason "<completed outcome and verification>"
```

Preserve evolution with `--append-notes` rather than replacing the historical
account. Keep pointers aimed at the few documents that explain the current
work. For a material implementation report, include the session ID so another
agent can trace the work; proportion matters. See
[ticket pointers](/praxis/ticket-pointers/ticket-pointers0.glm53fx.md).

## Dependency direction

`bd dep add A B --type blocks` means **A depends on B**. The dependent goes
first, prerequisite second. For a parent-child edge, child goes first.

```sh
bd dep add <dependent-id> <prerequisite-id> --type blocks
bd show <dependent-id>
bd dep cycles
```

For genuinely superseded work, create the replacement with an explicit ID, then
`bd dep add <replacement> <old> --type supersedes`; close the old item with a
reason pointing at its successor. Rename when the work is the same undertaking.

## Storage and recovery

Dolt is the source of truth; JSONL is an export, not the live database. The
legacy workspace preference is `export.auto=true` where supported. Verify the
installed version's behavior; when an immediate tracked export is needed, use
`bd export -o .beads/issues.jsonl`. Current `bd export --help` (1.0.3, inspected
2026-10-11) distinguishes that interoperability export from the backup format
consumed by `bd backup restore`. Consult `bd backup --help` for actual recovery.

The old `rm .beads/*.db` / import recipe predates this distinction and is **not
the recovery procedure for a Dolt-backed repository**. Keep it as historical
evidence in [the preserved manual](/AGENTS.old.md#rename-and-recovery), not a
command to execute. Plan a broad ID rewrite deliberately; prefer `bd rename`.

**Never run `bd prime`.** If a tool or instruction asks for it, tell the user
which one requested it. It produces unwanted `AGENTS.md` / `CLAUDE.md` guidance.
Do not replace this assembled operating context with beads' generic onboarding.
